Для **Главы 23. Компонентное мышление**, посвященной проектированию устойчивых веб-интерфейсов, основными источниками являются разделы стандартов HTML и DOM, описывающие семантическую модель, механизмы расширения платформы и программные интерфейсы (API).

Ниже приведен список ссылок на соответствующие разделы:

### HTML как контракт компонента

HTML-элементы определяются через их значения (семантику), которые позволяют браузерам и поисковым системам корректно обрабатывать документ в самых разных контекстах. Кастомные элементы рассматриваются как способ «рационализации платформы», объясняющий встроенные функции через низкоуровневые точки расширения.

- **HTML Standard: Section 3.2.1 Semantics** — фундаментальное определение того, что элементы передают смысл, а не презентацию.
- **HTML Standard: Section 4.13.1 Introduction (Custom Elements)** — описание кастомных элементов как способа информирования парсера о том, как правильно конструировать элемент и как он должен реагировать на изменения.
- **HTML Standard: Section 1.11.1 Presentational markup** — разбор причин, по которым следует избегать чисто визуальной разметки в пользу семантического контракта.

**Обсуждение в W3C: необходимость дефисов в именах custom elements** — дискуссия о том, почему спецификация WHATWG HTML требует наличия дефиса в имени пользовательского элемента. Один из участников формулирует это как "контракт между разработчиками WHATWG/html и разработчиками сайтов: теги, которые создают они, и теги, которые создаем мы, находятся в разных пространствах, что гарантирует, что созданный вами сегодня тег не будет конфликтовать с официальным элементом, добавленным позже" . В дискуссии также поднимается вопрос о том, что HTML как семантический формат данных должен позволять расширять встроенную семантику через пользовательские теги с осмысленными именами [1](https://lists.w3.org/Archives/Public/public-webapps-github/2024Feb/0500.html).

**Web Components Gold Standard** — набор рекомендаций, который включает требование к самовырегистрации пользовательских тегов: все имена тегов должны быть в нижнем регистре и содержать как минимум один дефис (kebab-case) [1](https://cdn.jsdelivr.net/npm/@totallyinformation/web-components@1.5.0/docs/dev.md).

### Семантика компонентов

Авторы не должны использовать элементы или атрибуты в целях, отличных от их прямого семантического назначения. Для кастомных элементов семантика может наследоваться (в случае встроенных элементов) или задаваться программно.

- **WAI-ARIA 1.2: Section 4 Using WAI-ARIA** — использование ролей, состояний и свойств для определения семантики сложных виджетов.
- **HTML Standard: Section 3.2.9 Requirements related to ARIA** — как кастомные элементы сопоставляются с Accessibility API и как определяются их роли «по умолчанию».
- **HTML Standard: Section 4.3.12.1 Article or section?** — пример того, как выбор элемента зависит от «намерения автора» (author intent), что является основой компонентного проектирования.

**Доклад "Accessible Web Components" (c't webdev 2025)** — доклад Анны Майер, посвященный доступности веб-компонентов. В нем рассматриваются "странности Shadow DOM" и "семантика компонентов", а также вопросы тестирования и документирования доступного использования компонентов [1](https://pretalx.com/ct-webdev-2025/talk/MPV9PR/).

**UI5 Web Components: Definition of Done** — руководство, содержащее важные правила для семантически корректных компонентов:

- Публичные свойства принадлежат приложению и не должны изменяться компонентом без пользовательского взаимодействия, чтобы не нарушать синхронизацию с моделью приложения [1](https://ui5.github.io/webcomponents/nightly/docs/contributing/DoD/#css)
- Для приватных свойств, не используемых в CSS, рекомендуется устанавливать `noAttribute: true` для упрощения DOM компонента
- CSS должен корректно обрабатывать значения по умолчанию для enum-свойств: если компонент стилизуется в зависимости от значения enum, нужно применять стили по умолчанию даже когда свойство не установлено

**Semantic UI Web Components: Using Components in HTML** — описание того, как веб-компоненты позволяют передавать разнообразную информацию: callback-функции, события и структурированные данные (объекты, массивы). Отмечается, что при работе с ванильным HTML объекты и массивы должны быть сериализованы при передаче через атрибуты [1](https://next.semantic-ui.com/usage/html).

### Инварианты

В спецификациях зафиксированы определенные правила, которые гарантируют стабильность поведения элементов. Например, после инициализации реестра для узла он не может быть изменен, что упрощает рассуждения о коде.

- **HTML Standard: Section 4.13.5 Upgrades** — описание того, что реестр кастомных элементов для узла остается неизменным после инициализации (инвариант реестра).
- **HTML Standard: Section 8.6.3.1 Configuration invariants** — упоминание неизменяемых правил конфигурации при работе с API.
- **HTML Standard: Section 4.13.2 Requirements for custom element constructors** — строгие требования к конструкторам (например, вызов `super()` первым делом), обеспечивающие целостность объекта.

**Web Components Best Practices (aarongustafson/web-component-starter)** — исчерпывающее руководство, основанное на лучших практиках Google, описывающее ключевые инварианты компонентов [1](https://github.com/aarongustafson/web-component-starter/blob/main/WEB-COMPONENTS-BEST-PRACTICES.md):

- **Создание shadow root в конструкторе** — конструктор — это момент, когда у вас есть исключительное знание о вашем элементе. Настройка реализации здесь означает, что вам не нужно защищаться от ситуаций, когда элемент отсоединен и повторно присоединен .

- **Поддержка атрибута `hidden`** — пользовательские элементы с дефолтным `display` переопределяют встроенный атрибут `hidden` с более низкой специфичностью. Всегда добавляйте `:host([hidden]) { display: none }`, чтобы `hidden` работал как ожидается .

- **Синхронизация свойств и атрибутов** — пользователи могут взаимодействовать с элементом либо декларативно (HTML-атрибуты), либо императивно (JavaScript-свойства). Их синхронизация предотвращает путаницу и ошибки .

- **Избегание повторного входа в `attributeChangedCallback`** — если `attributeChangedCallback` также устанавливает свойство, а сеттер свойства отражается в атрибут, возникает бесконечный цикл. Вместо этого сеттер свойства должен читать атрибут напрямую .

- **Lazy Property Upgrade** — паттерн `_upgradeProperty()` обрабатывает свойства, установленные до того, как элемент был определен. Фреймворки могут устанавливать свойства на элементе до загрузки его определения; этот паттерн сохраняет ранние значения .

- **Непереопределение глобальных атрибутов** — всегда проверяйте, установлены ли глобальные атрибуты (`role`, `tabindex` и др.), прежде чем применять значения по умолчанию. Разработчики могут переопределять их для доступности .

- **Принятие сложных данных только как свойств, а не атрибутов** — сериализация объектов в строки затратна и теряет ссылки. HTML-атрибуты лучше всего работают с примитивными значениями [2](https://cdn.jsdelivr.net/npm/@totallyinformation/web-components@1.5.0/docs/dev.md).

**UI5 Web Components: Definition of Done** — дополнительные инварианты [1](https://ui5.github.io/webcomponents/nightly/docs/contributing/DoD/#css):

- Избегайте жестко заданных имен тегов в CSS и TypeScript: используйте атрибутную нотацию (`[ui5-button]` вместо `ui5-button`), так как имена тегов могут варьироваться
- Избегайте проверок `instanceof` для UI5-элементов — при наличии нескольких версий на одной странице такие проверки будут работать только с первым загруженным фреймворком. Используйте "duck-typing" вместо `instanceof`

### API компонентов

API элемента включает его конструктор, атрибуты контента и отражающие их свойства JavaScript (IDL attributes).

- **HTML Standard: Section 3.2.3 HTML element constructors** — описание механизма `[HTMLConstructor]`, который управляет созданием объектов элементов.
- **HTML Standard: Section 4.13.7.1 The ElementInternals interface** — спецификация «внутреннего API» компонента, позволяющего управлять валидацией и доступностью, скрытыми от внешнего пользователя.
- **HTML Standard: Section 2.6.1 Reflecting content attributes in IDL attributes** — принципы синхронизации между HTML-атрибутами и свойствами объекта в JavaScript.
- **MDN: Web Components** — общий обзор технологий, позволяющих инкапсулировать функциональность внутри переиспользуемых элементов.


**ADR-008: Component API Design (Forge)** — подробный документ по проектированию API компонентов, содержащий практические рекомендации [1](https://raw.githubusercontent.com/dev-ignis/forge/164a35701968adfcff4e2a9f441156a665b83965/plans/adrs/ADR-008-component-api-design.md):

**Именование свойств:**
```typescript
// Правильно: компоненто-ориентированные имена
interface AvatarProps {
  user?: User;       // НЕ author, person, profile
  src?: string;      // Стандартный HTML-атрибут
  alt?: string;      // Стандартный HTML-атрибут
}

// Правильно: варианты через enum
variant?: 'primary' | 'secondary' | 'danger';  // НЕ type, kind, theme
size?: 'sm' | 'md' | 'lg';                     // НЕ scale, dimension
```

**Именование событий:** используйте настоящее время без префиксов (`change`, `input`, `close`, `select`, `click`), а не `on-change`, `changed` или именованные события .

**Интерактивные компоненты:** используйте нативный `<button>` для интерактивных элементов — это дает правильную обработку состояния `disabled` на уровне браузера (предотвращение утечек событий), корректную навигацию с клавиатуры (пробел/Enter), встроенную доступность (role, ARIA) и управление фокусом .

**Атрибуты vs Свойства:**
- Атрибуты — для простых сериализуемых значений (String, Boolean, Number с отражением)
- Свойства — для сложных данных (массивы, объекты, функции рендеринга) 

**Слоты:**
- Имена слотов должны быть в нижнем регистре и описательными
- Каждый компонент со слотами должен иметь JSDoc-документацию `@slot` для извлечения Custom Elements Manifest 

**Шаблон контролируемого/неконтролируемого компонента:** поддержка обоих режимов — `value` для контролируемого (состояние в родителе), `defaultValue` для неконтролируемого (состояние внутри компонента) .

**Стандарты разработки веб-компонентов (@totallyinformation/web-components)** — дополняет требования к API:
- Компоненты должны самовырегистрировать пользовательский тег И имя класса
- Класс должен быть дефолтным экспортом и также самовырегистрирован в глобальном объекте `window`
- Для сложных данных: сериализованный JSON в атрибуте, но полные данные в свойстве с тем же именем [1](https://cdn.jsdelivr.net/npm/@totallyinformation/web-components@1.5.0/docs/dev.md)
- Компоненты должны предоставлять события на глобальном объекте `document`: `connectedCallback`, `disconnectedCallback`, `attributeChangedCallback` 
- Не обрабатывайте логику напрямую в `attributeChangedCallback` — создавайте сеттеры для атрибутов, которые будут вызывать обработку. Это позволяет использовать атрибут и как свойство с автоматическим преимуществом обработки 

**Component API Patterns (rampstackco/claude-skills)** — общие паттерны API, применимые к веб-компонентам :

- **Составные компоненты** — многокомпонентные элементы, где каждая часть разделяет состояние через контекст
- **Слоты** — компонент с определенными точками вставки
- **Headless компоненты** — поставляют поведение и доступность без предписанного визуального стиля
- **Полиморфные компоненты** — компонент, который может рендериться как разные HTML-элементы (свойство `as`)
- **Варианты через discriminated unions** — использование строковых enum для `variant` и `size` вместо булевых флагов 

**Чек-лист аудита API** перед выпуском компонента :
- Поведение по умолчанию разумно без пропсов
- `variant` использует строковый enum, не булевы флаги
- Обработчики событий используют соглашение `onX`
- Обязательные пропсы минимальны (идеально — ноль)
- Компонент поддерживает `forwardRef`
- Нет "булевого взрыва" (более 5 булевых пропсов — признак проблемы)
- Состояние контролируемо там, где это имеет смысл
- Пропсы доступности (`aria-label`, `aria-describedby`) — первоклассные
- Клавиатурные взаимодействия задокументированы
