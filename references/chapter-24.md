### Design Tokens (Дизайн-токены и расширяемость)
Хотя термин «Design Tokens» является концепцией проектирования, HTML предоставляет механизмы для хранения и передачи таких данных на уровне элементов.

*   **HTML Standard: Section 3.2.6.6 Embedding custom non-visible data with the `data-*` attributes** — использование атрибутов данных для хранения пользовательской информации, состояний и аннотаций, специфичных для системы компонентов.
*   **HTML Standard: Section 1.7.2 Extensibility** — описание того, как авторы могут использовать атрибут `class` и `data-*` для расширения семантики элементов и создания собственных словарей внутри системы.
*   **HTML Standard: Section 3.2.6.5 The `style` attribute** — программный доступ к объекту `CSSStyleDeclaration` для применения динамических стилей (например, значений токенов) к элементам.
*   **MDN Guide: Layout cookbook** — примеры реализации стандартных компонентов дизайн-систем, таких как карточки (`Card component`) и колоночные макеты.


**Design Tokens Format Module 2025.10 (W3C Community Group Report)** — официальная стабильная спецификация формата дизайн-токенов, опубликованная 28 октября 2025 года. Документ описывает [1](https://lists.w3.org/Archives/Public/public-design-tokens/2025Oct/0003.html), [2](https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/):

- Формат файла для обмена дизайн-токенами между различными инструментами — единый источник истины для цветов, типографики, отступов и других дизайн-решений
- Стандартизированную поддержку тем и мульти-брендовости — управление светлыми/темными режимами, вариантами доступности и брендовыми темами без дублирования файлов
- Современные цветовые пространства — полную поддержку Display P3, Oklch и всех пространств CSS Color Module 4
- Богатые отношения между токенами — наследование, алиасы и ссылки на уровне компонентов
- Кросс-платформенную согласованность — один файл токенов генерирует платформо-специфичный код для iOS, Android, web и Flutter

Спецификация разработана при участии Adobe, Amazon, Google, Baidu, Sony, Microsoft, Meta, Sketch, Salesforce, Shopify, Figma, Framer, Cisco, Intuit, New York Times, GM, Disney, Pinterest и других организаций.

**GitLab Pajamas Design System: Authoring Design Tokens** — практическое руководство по созданию дизайн-токенов с использованием спецификации DTCG. Включает:

- Структуру именования токенов: `[group].[component].[variant/category].[element].[position].[relationship].[property].[type].[scale].[state]`
- Синтаксис токенов в формате `*.token.json` с обязательными свойствами `$value` и `$type`
- Примеры цветовых токенов с `colorSpace`, `components`, `alpha` и `hex`
- Использование алиасов через синтаксис `"{token.name}"` для создания ссылок на другие токены
- Расширения (`$extensions`) для дополнительной метаданных, например `com.figma.scopes` для интеграции с Figma

**Design Tokens Community Group GitHub Repository** — репозиторий для обсуждения и развития спецификации. Доступен по адресу: https://github.com/design-tokens/community-group/issues. Поддерживается ведущими инструментами: Style Dictionary, Tokens Studio, Terrazzo, Penpot, Figma, Sketch, Framer, Knapsack, Supernova, zeroheight.


### Семантическая структура (Semantic Structure)
Фундамент любой дизайн-системы — это правильное использование категорий контента для построения предсказуемой архитектуры страницы.

*   **HTML Standard: Section 3.2.1 Semantics** — фундаментальное определение того, что HTML передает смысл, позволяя процессорам (браузерам, поисковикам) использовать документы в самых разных контекстах.
*   **HTML Standard: Section 3.2.5.2 Kinds of content** — классификация элементов по категориям (`Flow`, `Sectioning`, `Heading`, `Phrasing`), что критично для определения контентных моделей компонентов.
*   **HTML Standard: Section 4.3.12 Usage summary** — сводная таблица по семантическому назначению основных структурных элементов (`article`, `section`, `nav`, `aside`), помогающая выбрать правильный «контракт» для компонента.

**WebAIM: Semantic Structure — Regions, Headings, and Lists** — всестороннее руководство по семантической структуре HTML, объясняющее [1](https://webaim.org/techniques/semanticstructure/?nav=2#headings):

- **Page regions** (`<header>`, `<nav>`, `<main>`, `<aside>`, `<footer>`): программно определяют существенную семантическую структуру страницы. Пользователи скринридеров могут легко перемещаться между этими основными областями. Рекомендуется наличие одного `<main>` на странице
- **Заголовки** (`<h1>`–`<h6>`): создают иерархию страницы. `<h1>` описывает страницу в целом (должен быть схож с `<title>`), не рекомендуется пропускать уровни (например, с `<h2>` на `<h4>`)
- **Списки** (`<ul>`, `<ol>`, `<dl>`): передают иерархическую структуру контента. Неупорядоченные списки — для контента без порядка, упорядоченные — для последовательности, списки определений — для пар "термин:описание"

**Rice University: Headings & Structure** — руководство по использованию семантических элементов для создания структуры страниц. Подчеркивает, что семантические элементы обеспечивают необходимую структуру для ассистивных технологий и улучшают визуальное восприятие [1](https://access.rice.edu/resources/web-content-accessibility-guidelines/headings-structure).

**Web Development Skills: Semantic HTML Reference (GitHub)** — подробный справочник по семантическим элементам для разработчиков веб-компонентов и дизайн-систем, содержащий:

- Таблицу использования семантических элементов: `header`, `footer`, `nav`, `main`, `aside`, `search`, `form`, `article`, `section`
- Правило: секция без доступного имени (`aria-labelledby`) ведет себя как `div` семантически
- Принцип: заголовки в переиспользуемых компонентах должны быть настраиваемыми — компонент может появляться в разных контекстах
- Различие между кнопками и ссылками: "Кнопки делают что-то, ссылки ведут куда-то" с учетом прогрессивного улучшения
- Семантику таблиц: `caption`, `thead`, `tbody`, `tfoot`, `th` с `scope`

**Educative: Section Headings and Semantic Hierarchy for Accessible UI** — объясняет связь между визуальной иерархией и семантической структурой. Подчеркивает, что для построения доступных интерфейсов необходимо продумывать семантическую структуру еще до написания кода. Ссылается на WCAG Guideline 1.3 (адаптивность — контент должен быть представлен без потери информации или структуры) [1](https://www.educative.io/courses/beginners-guide-to-web-accessibility/section-headings-and-semantic-hierarchy).

### Переиспользуемые шаблоны (Reusable Patterns)
Механизмы веб-платформы, позволяющие создавать изолированные и повторно используемые блоки интерфейса.

*   **HTML Standard: Section 4.12.3 The `template` element** — описание элемента для объявления инертных фрагментов разметки, которые могут многократно клонироваться скриптами системы.
*   **HTML Standard: Section 4.12.4 The `slot` element** — использование слотов как заполнителей внутри компонентов для распределения внешнего контента.
*   **HTML Standard: Section 4.13 Custom elements** — спецификация, позволяющая авторам определять собственные элементы с инкапсулированной логикой и жизненным циклом.
*   **MDN Guide: Web Components** — общее руководство по созданию переиспользуемых элементов, которые могут быть интегрированы в любое приложение.
*   **MDN Guide: Using shadow DOM** — принципы инкапсуляции стилей и структуры, гарантирующие, что компоненты дизайн-системы не будут случайно изменены внешним кодом.

**Ohio State University (BUX): Design Templates — Upgrading from PDF to HTML for Better Web Prototypes** — практический кейс создания HTML-шаблонов на основе дизайн-системы Buckeye UX 1.0. [1](https://bux.osu.edu/blog/html-templates/#overview) Демонстрирует:

- Трансформацию статических PDF-файлов в динамические HTML-шаблоны, которые служат отправной точкой для дизайнеров и разработчиков
- Использование компонентов дизайн-системы в шаблонах для создания эффективных, адаптивных веб-страниц
- Внедрение спецификаций типографики, цвета, глобальных значений отступов для обеспечения визуальной согласованности
- Комментарии в исходном коде для упрощения навигации и модификации шаблонов
- QA-тестирование не только отдельных компонентов, но и их комбинаций в реальных сценариях использования

**Popular Web Designs (GitHub moltis-org)** — коллекция из 54 production-ready дизайн-систем, извлеченных из реальных сайтов (Stripe, Linear, Vercel, Notion, Airbnb и др.). [1](https://github.com/moltis-org/moltis/blob/main/crates/skills/src/assets/creative/popular-web-designs/SKILL.md) Каждый шаблон включает:

- Полную цветовую палитру, иерархию типографики, стили компонентов, систему отступов, тени и адаптивное поведение
- Готовые CSS-значения и CDN-замены для проприетарных шрифтов (например, DM Sans для Circular Spotify, Source Sans 3 для sohne-var Stripe)
- Паттерн генерации HTML с использованием CSS-кастомных свойств для дизайн-токенов



### Accessibility by Design (Доступность как часть проектирования)
Интеграция семантики доступности в саму структуру компонентов дизайн-системы.

*   **WAI-ARIA 1.2: Section 5.3 Categorization of Roles** — разделение ролей на виджеты, структурные элементы и ориентиры (`Landmarks`) для создания логичной архитектуры доступности.
*   **ARIA Authoring Practices Guide (APG)** — руководство по внедрению семантики доступности в стандартные паттерны веб-виджетов.
*   **WAI-ARIA 1.2: Section 1.1 Rich Internet Application Accessibility** — концепция семантики как «науки о смысле», позволяющая вспомогательным технологиям понимать границы и поведение сложных компонентов.
*   **HTML Standard: Section 3.2.9 Requirements related to ARIA** — правила сопоставления кастомных элементов с Accessibility API и определение их ролей по умолчанию.
*   **WAI-ARIA 1.2: Section 5.2.8 Accessible Name Calculation** — алгоритмы вычисления имен элементов, что является ключевым для создания подписей к компонентам дизайн-системы.


**Inclusive By Design: HTML Forms Best Practices (University of Minnesota)** — руководство по доступным формам, охватывающее [1](https://inclusive-design.umn.edu/forms/):

- **Маркировку элементов форм**: программная связь `label` с `for` — не только для скринридеров, но и для увеличения кликабельной области (полезно для пользователей с нарушениями моторики)
- **Группировку наборов элементов**: использование `role="group"` и `aria-labelledby` для логической группировки связанных элементов формы (радиокнопки, чекбоксы)
- **Обязательные поля**: индикаторы не должны полагаться только на цвет; должны быть программно связаны с полем; легенда в начале формы

**Access by Design: A Guide to Universal Usability for Web Designers (Sarah Horton)** — фундаментальная книга о дизайне для универсальной доступности [1](https://franklin.library.upenn.edu/catalog/FRANKLIN_9977533345703681) [2](https://search.worldcat.org/zh-cn/title/access-by-design-a-guide-to-universal-usability-for-web-designers/oclc/61310052/lists). Ключевые идеи:

- Простое соблюдение официальных стандартов и руководств по доступности недостаточно — цель должна быть в **универсальной юзабилити**
- Методология дизайна выходит за рамки требований доступности, чтобы оптимизировать страницы для большего числа пользователей, с инвалидностью или без
- Четкие принципы использования HTML и CSS для всех функциональных элементов веб-сайтов: текст, формы, изображения, таблицы, фреймы, ссылки, интерактивность, верстка страниц
- Аргумент: хорошие принципы дизайна приносят пользу всем пользователям веба

**Web Development Skills: Code Review Checklist for Semantic HTML** — чек-лист для проверки доступности разметки, включающий [1](https://raw.githubusercontent.com/NeverSight/skills_feed/refs/heads/main/data/skills-md/schalkneethling/webdev-agent-skills/semantic-html/SKILL.md):

- **Позитивные сигналы**: правильное использование landmark-элементов, логическая иерархия заголовков, нативные интерактивные элементы, формы с правильными лейблами и полями, полная семантическая структура таблиц, ARIA используется сдержанно и правильно
- **Тревожные сигналы**: большое количество `<div>` в не-сложных компонентах, ARIA-атрибуты для компенсации отсутствующей нативной семантики, плейсхолдеры как лейблы, уровни заголовков по визуальному размеру (а не структуре), `click`-обработчики на generic-элементах вместо кнопок/ссылок, таблицы для верстки, пропущенные лейблы форм
