Для **Главы 26**, посвященной разработке полностью современного приложения, основными источниками служат спецификации HTML и DOM, а также руководства MDN и web.dev. Эти материалы описывают техническую базу для создания интерактивных, производительных и доступных интерфейсов.

Ниже приведен список ссылок, сгруппированный по ключевым технологиям главы:

### Семантический HTML и структура

Основа приложения — использование элементов согласно их внутреннему смыслу (семантике), что обеспечивает доступность и корректную обработку браузерами.

- **HTML Standard: Section 3.2.1 Semantics** — фундаментальное определение того, что элементы передают смысл, а не презентацию.
- **HTML Standard: Section 4.3.12 Usage summary** — правила использования структурных элементов, таких как `article`, `section`, `nav`, `aside` и `header`/`footer`.
- **WAI-ARIA 1.2: Section 5.3 Categorization of Roles** — описание ролей элементов для создания корректного дерева доступности.

**GitHub Forge: Semantic HTML Best Practices** — подробное руководство по использованию семантического HTML для создания доступных и SEO-оптимизированных компонентов. Документ описывает [1](https://github.com/dev-ignis/forge/blob/main/docs/semantic-html-best-practices.md):

- **Тройной выигрыш семантики**: семантический HTML одновременно приносит пользу AI-системам (понимание назначения и связей компонентов), скринридерам (навигация и корректное озвучивание контента) и поисковым движкам (индексация и ранжирование)
- **Соглашение об именовании семантических ролей**: паттерн `категория-специфическое-действие` (`nav-*`, `form-*`, `dialog-*`, `data-*`, `user-*`, `search-*`, `filter-*`, `sort-*`)
- **Контекстные иерархии AI**: построение деревьев контекста от общего к частному через атрибут `ai-context` с наследованием от родителей
- **Анти-паттерны**: слишком общие роли, пропущенные ARIA-лейблы для иконок, конфликтующие ARIA-атрибуты, изолированный контекст без полного пути

**Elegant Themes: Semantic Elements in Divi 5** — практическое руководство с объяснением, почему семантические элементы важны:

- **Более четкая структура и организация**: семантические теги превращают разметку из коллекции generic-контейнеров в логически организованную карту [2](https://www.elegantthemes.com/blog/divi-resources/everything-you-need-to-know-about-semantic-elements-in-divi-5)
- **Лучший парсинг поисковыми системами**: четкая семантика дает сильные контекстуальные сигналы для AI-поиска, помогая таким функциям как rich snippets и featured results
- **Улучшенный UX и доступность**: теги `nav` и `main` позволяют пользователям скринридеров эффективно навигировать, а `button` корректно объявляет интерактивные элементы
- **Советы и лучшие практики**: всегда выбирайте теги на основе назначения контента, а не его внешнего вида; соблюдайте логическую иерархию заголовков (одно H1 на страницу)

### Элемент `<dialog>`

Использование нативного элемента для создания модальных и немодальных окон с автоматическим управлением фокусом и инертностью остальной части страницы.

- **MDN: `<dialog>` HTML dialog element** — общее руководство по использованию и доступности.
- **HTML Standard: Section 4.11.4 The `dialog` element** — детальная спецификация методов `showModal()`, `show()` и `close()`.
- **HTML Standard: Section 6.3.1 Modal dialogs and inert subtrees** — механизм блокировки взаимодействия с фоновым контентом.

**MDN Web Docs: `<dialog>` Element** — официальная документация HTML-элемента диалога [1](https://mdn.org.cn/en-US/docs/Web/HTML/Element/dialog):

- **Модальные и немодальные диалоги**: использование `.showModal()` для модальных (блокирующих взаимодействие с остальной страницей) и `.show()` для немодальных
- **Закрытие диалога**: через `.close()` или при отправке `<form method="dialog">`; модальные диалоги также закрываются по клавише Escape
- **Стилизация фона**: CSS-псевдоэлемент `::backdrop` для затемнения или размытия неактивного контента за модальным диалогом
- **Управление фокусом**: атрибут `autofocus` должен быть добавлен на элемент, с которым пользователь должен взаимодействовать сразу после открытия; если сомневаетесь — сам `<dialog>` может быть лучшим местом для начального фокуса
- **Доступность**: `<dialog>` с `showModal()` неявно имеет `aria-modal="true"`; весь контент вне диалога автоматически становится инертным; `tabindex` не должен использоваться на `<dialog>`

**WHATWG Mailing List (2008)** — историческое обсуждение именования элемента `<dialog>`: в спецификации термин "dialog" использовался одновременно для "диалоговых окон" (dialog boxes) и "разговоров" (conversations), что вызывало путаницу в сообществе [2](https://lists.whatwg.org/pipermail/whatwg-whatwg.org/2008-May/014790.html).

### Popover API

Современный стандарт для создания всплывающих элементов (меню, подсказок), которые рендерятся в «верхнем слое» (top layer).

- **MDN: Popover API** — обзор концепций и атрибутов `popover`, `popovertarget`.
- **HTML Standard: Section 6.12 The `popover` attribute** — техническое описание состояний `auto` и `manual`, а также логики «легкого закрытия» (light dismiss).
- **HTML Standard: Section 6.12.1 The popover target attributes** — работа атрибутов активации на кнопках.

**MDN Web Docs: Popover API** — всесторонняя документация API для отображения всплывающего контента поверх страницы:

- **Определение**: Popover API предоставляет стандартный, согласованный и гибкий механизм для отображения всплывающего контента над другим содержимым страницы [1](https://mdn.org.cn/en-US/docs/Web/API/Popover_API) [2](https://developer.mozilla.org/en-US/docs/Web/API/Popover_API)
- **HTML-атрибуты**:
  - `popover` — глобальный атрибут, превращающий элемент в popover (значения: `"auto"`, `"hint"`, `"manual"`)
  - `popovertarget` — превращает `<button>` или `<input>` в кнопку управления; значение — ID целевого popover-элемента
  - `popovertargetaction` — действие для popover (`"hide"`, `"show"`, `"toggle"`)
- **Концепция**: popover всегда немодальный (в отличие от `<dialog>`), хотя `dialog popover` — полностью валидная комбинация, сочетающая управление popover с семантикой диалога
- **Варианты использования**: меню действий, кастомные "Toast" уведомления, подсказки для элементов форм, селекторы контента или обучающие UI

**Примечание**: Popover API стал доступен с января 2025 года. Части функциональности могут иметь разный уровень поддержки в разных браузерах.

### Web Components и Declarative Shadow DOM

Инструменты для создания инкапсулированных переиспользуемых компонентов, поддерживающих серверный рендеринг (SSR).

- **MDN: Web Components** — введение в технологии Custom Elements, Shadow DOM и HTML Templates.
- **HTML Standard: Section 4.13 Custom elements** — регистрация элементов и управление их жизненным циклом.
- **MDN: Shadow DOM — Declaratively with HTML** — использование атрибута `shadowrootmode` у элемента `<template>` для немедленной отрисовки теневого дерева.

**WHATWG HTML Spec: Declarative Shadow DOM** — официальная спецификация, описывающая синтаксис через атрибут `shadowrootmode` на элементе `<template>` [1](https://raw.githubusercontent.com/mfreed7/declarative-shadow-dom/822bb0e27b0eed3235b2338006a87fa683559e36/README.md).

**Web.dev: Declarative Shadow DOM** — исчерпывающее руководство (автор Mason Freed):

- **Мотивация**: SSR требует отображения контента без выполнения JavaScript — для SEO, производительности и поддержки пользователей с отключенным JS. Императивный API Shadow DOM несовместим с этими требованиями [2](https://web.dev/articles/declarative-shadow-dom?hl=en)
- **Синтаксис**: `<template shadowrootmode="open">` внутри элемента-хоста. Парсер при встрече этого тега:
  1. Переключается в режим "in template"
  2. Парсит дочернее содержимое в DocumentFragment
  3. При закрытии `</template>` создает shadow root, перемещает содержимое в него и удаляет пустой `<template>` из DOM
- **Результирующее DOM-дерево**:

```html
<host-element>
  #shadow-root (open)
  <style>
    shadow styles
  </style>
  <h2>Shadow Content</h2>
  <slot>
    ↳
    <h2>Light content</h2>
  </slot>
</host-element>
```

- **Поддержка стилей**: инлайн и внешние стили через `<style>` и `<link>` полностью поддерживаются; если один файл стилей используется в нескольких Declarative Shadow Roots, он загружается и парсится только один раз (общий `CSSStyleSheet`)
- **Streaming**: Declarative Shadow Roots обнаруживаются во время парсинга и применяются сразу; парсенный HTML внутри `<template>` напрямую попадает в shadow root, что позволяет "стримить" контент по мере получения
- **Parser-only**: Declarative Shadow Root создается только при наличии `shadowrootmode` в начальном парсинге HTML; установка этого атрибута через JavaScript не работает
- **Hydration компонентов**: Custom Element, у которого уже есть Declarative Shadow Root, получает его через `ElementInternals.shadowRoot` до того, как код явно создаст его через `attachShadow()`
- **Feature detection**: `HTMLTemplateElement.prototype.hasOwnProperty('shadowRootMode')`
- **Предотвращение FOUC**: использование CSS-правила `x-foo:not(:defined) > template[shadowrootmode] ~ * { display: none; }` — в браузерах с DSD поддержкой `<template>` удаляется, в браузерах без поддержки он сохраняется и скрывает нестилизованный контент до загрузки полифилла

#### Web Components

**GitHub Forge: ADR-008 Component API Design** — архитектурное решение по проектированию API веб-компонентов:

- **Свойства vs Атрибуты**: атрибуты — для простых сериализуемых значений (String, Boolean, Number с отражением); свойства — для сложных данных (массивы, объекты, функции рендеринга)
- **Именование булевых свойств**: позитивные, описательные имена (`disabled`, `loading`, `checked`, `open`, `readonly`), префикс `is` только для нестандартных состояний (`isActive`, `isHovered`)
- **Именование вариантов**: `variant` (не `type`, `kind`, `theme`), `size` (не `scale`, `dimension`), `position` (не `placement`, `align`)
- **Именование событий**: настоящее время без префиксов (`change`, `input`, `close`, `select`, `click`), а не `on-change`, `changed` или именованные события
- **Использование нативных `<button>`**: для интерактивных компонентов — даёт правильную обработку `disabled` на уровне браузера, корректную навигацию с клавиатуры (пробел/Enter), встроенную доступность (role, ARIA) и управление фокусом
- **Слоты**: все компоненты со слотами должны иметь JSDoc `@slot` для Custom Elements Manifest; имена слотов в нижнем регистре и описательные
- **Шаблон контролируемого/неконтролируемого компонента**: `value` для контролируемого (состояние в родителе), `defaultValue` для неконтролируемого (состояние внутри компонента)

### Современные формы и валидация

Использование встроенных механизмов проверки данных и новых атрибутов для улучшения пользовательского опыта.

- **HTML Standard: Section 4.10.21 Constraints** — описание декларативной валидации (атрибуты `required`, `pattern`, `minlength`).
- **HTML Standard: Section 4.10.21.3 The constraint validation API** — программный интерфейс для управления проверками через `checkValidity()` и `setCustomValidity()`.
- **HTML Standard: Section 6.8.9/10 Input modalities** — настройка виртуальных клавиатур через `inputmode` и `enterkeyhint`.

**MDN Web Docs: `<dialog>` and forms** — использование `<form method="dialog">` внутри `<dialog>` для автоматического закрытия диалога при отправке с сохранением состояния формы.

**FormValidation: AutoFocus Plugin** — документация плагина для автоматического фокуса на первом невалидном поле при отправке формы, с опцией `onPrefocus` для доступа к имени поля и первому невалидному элементу.

**GitHub Forge: Semantic Form Patterns** — практические примеры семантических форм:

- Использование `search` landmark с атрибутом `role="search"` и элементов `forge-input`, `forge-button`, `forge-select`
- Формы с валидацией: `required`, `aria-required="true"`, `aria-describedby` для сообщений об ошибках, `role="alert"` для динамических сообщений
- Группировка элементов формы через `role="group"` и `aria-labelledby`

### Оптимизация и Resource Hints

Механизмы подсказок браузеру для ускорения загрузки критических ресурсов.

- **HTML Standard: Section 4.6.8 Link types** — спецификации для `rel="preload"`, `rel="prefetch"`, `rel="preconnect"` и `rel="dns-prefetch"`.
- **HTML Standard: Section 4.2.4.5 Early hints** — использование HTTP-статуса 103 для опережающей загрузки ресурсов.
- **HTML Standard: Section 2.5.9 Fetch priority attributes** — управление приоритетами запросов через атрибут `fetchpriority`.

**React DOM Resource Hints (GitHub)** — описание API для подсказок ресурсов, адаптированных для React:

- **`prefetchDNS(href)`** — разрешение DNS для домена, к которому планируется подключение
- **`preconnect(href)`** — установка соединения (DNS + TCP + TLS) с сервером
- **`preload(href, options)`** — загрузка ресурса (stylesheet, font, script, image), который скоро понадобится
- **`preloadModule(href)`** — загрузка ES-модуля
- **`preinit(href, options)`** — загрузка и выполнение stylesheet или script
- **`preinitModule(href)`** — загрузка и выполнение ES-модуля

**Примеры использования**:

```jsx
import { preconnect, prefetchDNS } from 'react-dom';
export default function App() {
  prefetchDNS('https://analytics.example.com');
  preconnect('https://api.example.com');
  return <main>{/* content */}</main>;
}
```

```jsx
import { preload, preinit } from 'react-dom';
export default function RootLayout({ children }) {
  preload('/fonts/inter.woff2', {
    as: 'font',
    type: 'font/woff2',
    crossOrigin: 'anonymous',
  });
  preinit('/styles/critical.css', { as: 'style' });
  return (
    <html>
      <body>{children}</body>
    </html>
  );
}
```

**Когда использовать**:

- `prefetchDNS` — сторонние домены, к которым будет подключение позже
- `preconnect` — API или CDN, с которых будет загрузка сейчас
- `preload` — критические ресурсы для текущей страницы
- `preloadModule` — JS-модули для вероятной следующей навигации
- `preinit` — stylesheet/скрипты, которые должны выполниться рано
- `preinitModule` — ES-модули, которые должны выполниться рано

### View Transition API и Navigation API

Создание плавных переходов между состояниями приложения и управление историей навигации.

- **HTML Standard: Section 7.2.6 The navigation API** — современная замена интерфейсу `history` для веб-приложений.
- **MDN: Critical rendering path** — понимание этапов рендеринга для эффективного применения анимаций перехода.

**CSS View Transitions Module Level 2 (W3C Editor Draft)** — официальная спецификация CSSWG:

- **Определение**: API позволяет создавать анимированные визуальные переходы между разными состояниями документа или элемента, или между различными документами одного origin
- **Уровень 2 добавляет**: кросс-документные переходы (`@view-transition` rule), селективные переходы, общие стили для псевдоэлемментов (`view-transition-class`), вложенные группы, scoped-переходы
- **Разделение визуальных переходов и DOM-обновлений**: традиционно для перехода требовалось одновременное присутствие обоих состояний в DOM. View Transitions позволяют мгновенно переключить DOM, а затем выполнить кастомизируемый визуальный переход в отдельном слое, используя статический слепок старого состояния и live-слепок нового
- **Жизненный цикл перехода**:
  1. Вызов `document.startViewTransition(updateCallback)`
  2. Захват текущего состояния как "старого"
  3. Пауза рендеринга внутри root-элемента
  4. Вызов `updateCallback` (обновление DOM)
  5. Захват нового состояния
  6. Создание псевдоэлементов перехода
  7. Снятие паузы рендеринга
  8. Анимация псевдоэлементов
  9. Удаление псевдоэлементов
- **Переход как улучшение**: анимированный переход — это визуальное улучшение изменения состояния документа. Неудача при создании перехода не должна предотвращать вызов `updateCallback` и обновление состояния. Даже если вызвать `skipTransition()` в начале жизненного цикла, `updateCallback` все равно выполнится
- **Customization**: по умолчанию — кросс-фейд всего root-элемента. Разработчик может выбрать отдельные элементы для независимого захвата через CSS-свойство `view-transition-name`

### Прогрессивное улучшение (Progressive Enhancement)

Философия создания устойчивых приложений, сохраняющих базовую функциональность в любых условиях.

- **HTML Standard: Section 4.13.1.6 Upgrading elements after their creation** — процесс «апгрейда» элементов как пример PE.
- **HTML Standard: Section 4.10.21.4 Security** — примечание о том, что клиентская валидация — это улучшение UX, а не замена серверной безопасности.
- **web.dev: Learn PWA** — учебный курс по созданию надежных веб-приложений на базе современных стандартов.

**Seobility Wiki: Progressive Enhancement** — определение и объяснение стратегии:

- **Определение**: прогрессивное улучшение — стратегия дизайна и разработки, которая начинается с простой основы и добавляет улучшения шаг за шагом для более мощных систем
- **Отличие от graceful degradation**: PE идет от простого к сложному, graceful degradation — от сложного к простому. При PE изменение браузера или расширения требует добавления функциональности без изменения исходного решения; при graceful degradation требуется модифицировать оригинальную версию
- **Три уровня**:
  1. Чистый, семантический HTML (работает в текстовых, языковых и старых user agent)
  2. CSS — браузер, не поддерживающий свойство, просто игнорирует его. Пример: `background: #999; background: rgba(153,153,153,.75);`
  3. JavaScript — интерактивность как улучшение
- **Feature queries**: `@supports (display: flex) { }` — стили применяются только если браузер поддерживает указанное свойство
- **Совместимость с Mobile First**: обе стратегии начинают с разработки для самой слабой системы (смартфон) и постепенно расширяют функциональность для более мощных устройств
- **Ограничения**: сложные фронтенд-интерфейсы сложно строить на основе PE, так как не всегда возможно создать простую базовую версию со сравнимой функциональностью

**GitHub Forge: API Design with Progressive Enhancement** — компоненты должны работать без JavaScript:

```html
<my-details open>
  <span slot="summary">Click to expand</span>
  <p>Content revealed when open</p>
</my-details>
```

Эти источники охватывают все технологии, необходимые для построения полностью современного приложения: от фундаментальной семантической разметки через современные UI-паттерны (`<dialog>`, Popover API) и энкапсуляцию (Declarative Shadow DOM, Web Components) до оптимизации загрузки (Resource Hints) и плавных переходов (View Transitions) — все с соблюдением принципов Progressive Enhancement.
