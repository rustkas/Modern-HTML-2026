Для **Главы 25**, посвященной современным подходам к серверному рендерингу (SSR) и архитектурам веб-приложений, основными источниками в предоставленных материалах являются разделы спецификаций HTML и DOM, описывающие **Declarative Shadow DOM**, механизмы **потокового парсинга** и **апгрейда элементов**.

Ниже приведен список ссылок на технические фундаменты, на которых строятся такие решения, как React Server Components, Astro и Qwik:

### Declarative Shadow DOM (Основа для SSR компонентов)
Механизм декларативного теневого DOM является ключевым для передачи инкапсулированных стилей и структуры компонентов с сервера без обязательного использования JavaScript для инициализации.

*   **HTML Standard: Section 4.12.3 The `template` element** — техническое описание атрибута `shadowrootmode` (`open`/`closed`), позволяющего браузеру отрисовывать теневое дерево немедленно при парсинге.
*   **HTML Standard: Streaming declarative shadow roots** — спецификация атрибутов, управляющих поведением теневых корней при потоковой передаче данных с сервера (например, `shadowrootclonable`, `shadowrootserializable`).
*   **MDN: Using shadow DOM — Declaratively with HTML** — практическое объяснение того, почему декларативный подход в SSR обеспечивает лучшую производительность и пользовательский опыт.

### Механизмы гидратации и прогрессивного улучшения
В контексте стандартов процесс «гидратации» (оживления серверной разметки на клиенте) описывается через алгоритмы создания и обновления элементов.

*   **HTML Standard: Section 4.13.1.6 Upgrading elements after their creation** — описание процесса «апгрейда», когда кастомные элементы (уже отрисованные через SSR) «оживают» и получают свою логику после загрузки и регистрации соответствующих скриптов.
*   **HTML Standard: Section 13.2 Parsing HTML documents** — фундаментальное описание того, как браузер превращает поток байтов из сети в живое дерево DOM, что критично для понимания **Streaming HTML**.

### Динамическая вставка и безопасность (Инструменты фреймворков)
Фреймворки часто используют специализированные API для эффективной вставки и обновления HTML-кода, полученного с сервера.

*   **HTML Standard: Section 8.5 DOM parsing and serialization APIs** — спецификация методов, таких как `innerHTML` и `insertAdjacentHTML()`, которые используются для динамического обновления контента.
*   **MDN: ShadowRoot.setHTMLUnsafe()** — описание современных методов вставки HTML, которые корректно обрабатывают декларативные теневые корни при динамическом обновлении страницы.

### Производительность и Critical Rendering Path
Концепции **Islands Architecture** и частичной гидратации направлены на оптимизацию пути рендеринга.

*   **MDN Guide: Critical rendering path** — определение последовательности шагов, которые браузер проходит для превращения кода в пиксели, что является главной целью оптимизации в SSR.
*   **HTML Standard: Section 3.1.6 Render-blocking mechanism** — описание элементов, которые могут приостанавливать отрисовку страницы, и способов управления ими.

### Angular SSR

**Официальная документация Angular: Server-side rendering** — подробное руководство по настройке и использованию SSR в Angular. Документ описывает [1](https://angular.dev/guide/ssr):

- **Преимущества SSR**: улучшенная производительность, улучшение Core Web Vitals (FCP, LCP, CLS), лучшее SEO 
- **Включение SSR**: команды `ng new --ssr` для нового проекта и `ng add @angular/ssr` для существующего 
- **Конфигурация сервера**: использование `CommonEngine` для рендеринга Angular-приложений на Node.js Express сервере 
- **Гибридный рендеринг**: Angular поддерживает комбинацию SSR, предварительного рендеринга (SSG) и клиентского рендеринга (CSR) через конфигурацию `ServerRoute` с режимами `RenderMode.Server`, `RenderMode.Prerender` и `RenderMode.Client` 
- **Совместимость с сервером**: использование хуков `afterRender` и `afterNextRender` для выполнения browser-specific кода только на клиенте 
- **Кэширование HttpClient**: ответы кэшируются на сервере и передаются клиенту для избежания повторных запросов во время гидратации

### React Server Components

**Официальная документация React: Server Components** — фундаментальное руководство по RSC, объясняющее [1](https://ar.react.dev/reference/rsc/server-components#async-components-with-server-components):

- **Определение**: Server Components рендерятся до сборки (на CI сервере или для каждого запроса) в среде, отдельной от клиентского приложения или SSR-сервера 
- **Async компоненты**: Server Components могут быть асинхронными и использовать `await` внутри рендера 
- **Использование без сервера**: рендеринг на этапе сборки для чтения из файловой системы или статического контента 
- **Использование с сервером**: прямой доступ к слою данных без необходимости создания API 
- **Интерактивность**: добавление клиентской интерактивности через директиву `"use client"` 
- **Паттерн `use`**: создание промиса на сервере и его ожидание на клиенте с помощью `use` API 

**Дополнительная документация по RSC** — содержит практические примеры:
- Паттерны загрузки данных с кэшированием (`cache: 'no-store'`, `next: { revalidate: 60 }`, теги для ревалидации)
- Параллельная и последовательная загрузка данных через `Promise.all`
- Прямой доступ к базе данных из Server Components
- Конфигурация `generateStaticParams` для предварительного рендеринга динамических маршрутов

### Astro

**Официальная документация Astro: Islands Architecture** — ключевой источник по архитектуре островов [1](https://github.com/withastro/docs/blob/main/src/content/docs/en/concepts/islands.mdx?plain=1) [2](https://docs.astro.build/en/concepts/islands/?trk=public_post_comment-text):

- **Определение**: архитектура рендерит большую часть страницы в быстрый, статический HTML с меньшими "островами" JavaScript, которые добавляются там, где нужна интерактивность 
- **История**: термин "component island" впервые введен Кэти Сайлор-Миллер из Etsy в 2019 году, расширен Джейсоном Миллером (создателем Preact) в августе 2020 года 
- **Клиентские острова**: интерактивные UI-компоненты, которые гидратируются отдельно от остальной страницы. Управляются через `client:*` директивы (`client:load`, `client:idle`, `client:visible`) 
- **Серверные острова**: UI-компоненты, которые рендерят динамический контент отдельно от остальной страницы через `server:defer` директиву 
- **Преимущества**: параллельная загрузка островов, JavaScript загружается только для явно отмеченных компонентов, поддержка множества UI-фреймворков (React, Preact, Svelte, Vue, SolidJS) 

**Статья "Astro Islands: The Architecture of Performance"** — дополнительный аналитический материал [1](https://feature-sliced.design/vi/blog/astro-islands-architecture):
- Сравнение традиционных SPA (полная гидратация) и Astro (частичная гидратация)
- Преимущества предсказуемой производительности и изоляции компонентов
- Интеграция с Feature-Sliced Design для масштабируемых проектов 

**Tencent Cloud: Islands Architecture** — русскоязычный обзор с объяснением [1](https://cloud.tencent.com.cn/developer/article/2397235?from=15425&frompage=seopage):
- Концепция "Import On Interaction"
- Сравнение с прогрессивной гидратацией
- Примеры реализации в Marko, Astro, Eleventy + Preact
- Преимущества и ограничения архитектуры

### Qwik

**Официальная документация Qwik: Overview** — описание фреймворка [1](https://media-updates.qwik-docs.pages.dev/docs/overview/):

- **Ключевая идея**: Qwik приложения загружаются с ~1kb JS (независимо от сложности) за счет концепции "Resumable" вместо Hydration 
- **Resumability**: приложения не требуют гидратации — они "возобновляют" выполнение с того места, где остановился сервер 
- **Производительность**: инкрементальная загрузка JS только по мере необходимости; примеры: 100ms быстрее → +1% конверсий, 1 секунда задержки → -10% пользователей 

**Qwik Tutorial Overview** — описание философии:
- Загрузка и выполнение только строго необходимого кода для пользовательских действий [2](https://speculative-modules-docs.qwik-docs.pages.dev/tutorial/welcome/overview/)
- Тонкая гранулярность ленивой загрузки (fine-grained lazy-loading) 

**Qwik Documentation: Progressive Concept** — объяснение механизмов:
- **Оптимизатор**: кодовая трансформация, извлекающая функции в импортируемые символы, позволяющие ленивую загрузку 
- **Синтаксис `$`**: маркер для оптимизатора, указывающий, что функция должна загружаться лениво 
- **Асинхронность**: Qwik — асинхронный фреймворк, понимающий что в любой момент может потребоваться ленивая загрузка кода 
- **Загрузка по требованию**: компоненты (при рендеринге), обработчики событий (при взаимодействии), стили (если не предоставлены сервером) — все загружается лениво

### Hydration

**Официальная документация Angular: Hydration** — определение процесса:

- **Гидратация** — процесс восстановления серверно-отрендеренного приложения на клиенте, включающий повторное использование DOM-структур, сохранение состояния приложения и передачу данных 
- В Angular гидратация включена по умолчанию при использовании SSR 
- Настройка кэширования HTTP-запросов через `provideClientHydration(withHttpTransferCacheOptions(...))` 

**Архитектура островов (Astro)** — объяснение через концепцию частичной гидратации:

- **Частичная (селективная) гидратация** — техника, лежащая в основе архитектуры островов 
- В отличие от SPA, гидратирующих всё приложение, Astro гидратирует только отдельные компоненты, отмеченные `client:*` директивами 
- Гидратация происходит независимо для каждого острова: низкоприоритетный карусель не блокирует высокоприоритетный хедер 

**Tencent Cloud: Islands Architecture** — сравнительный анализ:
- Традиционная SSR гидратация: требуется полная гидратация страницы, даже для маленьких виджетов
- Частичная гидратация в островах: только интерактивные компоненты получают JavaScript

### Islands Architecture

**Официальная документация Astro** — наиболее полный источник по архитектуре островов:

- **Определение**: остров — это улучшенный UI-компонент на статической HTML-странице. "Интерактивный виджет, плавающий в море статического HTML" 
- **Клиентские острова**: гидратируются отдельно, JS загружается только для явно отмеченных компонентов через `client:*` директивы 
- **Серверные острова**: для динамического контента, рендерящегося отдельно через `server:defer` 
- **Изоляция**: каждый остров работает изолированно, хотя может обмениваться состоянием с другими 
- **Поддержка фреймворков**: React, Preact, Svelte, Vue, SolidJS, можно смешивать на одной странице 

**Аналитическая статья Feature-Sliced Design** — архитектурные аспекты:
- **Сравнение подходов**: SPA (полная гидратация, высокий JS-кост, медленный TTI) vs Частичная гидратация (минимальный JS, быстрая интерактивность) 
- **Инверсия контроля**: Astro рендерит в статический HTML по умолчанию, разработчик явно "оптится" в интерактивность 
- **Предсказуемость**: характеристики производительности явные и локальные, а не эмерджентные и глобальные
